# 工程实践与部署经验

> 本文记录本项目在**大规模双臂策略训练与云端部署**过程中沉淀的工程经验，
> 源自真实踩坑与修复，供复现与二次开发参考。对应评审维度「工程实现与可运行性」。

## 1. 训练数据生命周期管理（防磁盘堆积）

**问题**：12 任务 × ~41G 转换数据 + 检查点，若管理不当会迅速占满磁盘，导致训练中途崩溃。

**经验**：
1. **转换数据（processed_data）按任务生命周期管理**：任务训练完成并**成功上传服务器后立即清理**，仅保留活跃任务的数据；
2. **上传失败必须留痕**：上传未成功时不清理（防止 ckpt 丢失），但要有**独立 watcher 兜底补传**（见 §3）；
3. **磁盘水位监控**：转换前检查可用空间，低于阈值（如 2×单任务转换量）时暂停预转换；
4. **图像逐帧 gzip 压缩存储**：单任务转换数据从 ~116G 降至 ~41G，显著降低磁盘压力（见技术方案 §5.1）。

## 2. SSH 连接频率管理（避免触发服务器限流）

**问题**：对共享服务器高频 SSH 尝试（训练上传 + watcher 轮询 + 手工检查叠加）会触发 sshd **连接限流**（MaxStartups 类），表现为 SSH 握手间歇性重置，上传频繁失败。

**经验**：
1. **控制连接频率**：低频连接（间隔 ≥30-60s）即可稳定访问；高频重试反而加剧限流；
2. **集中连接**：避免多进程（驱动、watcher、手工）同时打 SSH，任务检查与上传错峰；
3. **SSH 检查加重试**：对"是否已上传"的检查做多次重试，避免瞬时失败误判导致重复训练（曾因此误重训已完成任务）；
4. **故障缓解**：判定为限流时停止所有 SSH 尝试等待恢复（约 60s-数分钟），再单次测试后恢复。

## 3. 大文件可靠上传（断点续传 + 完整性校验）

**问题**：335MB 检查点经不稳链路 scp 中断后，服务器文件不完整（少几百 KB），若未校验将部署损坏模型。

**经验**：
1. **用 `rsync --partial` 代替 scp**：中断后重跑即从断点续传，可靠传输大文件；
   ```bash
   rsync -P --partial -e "ssh -o ConnectTimeout=15" policy_best.ckpt user@server:/path/policy_last.ckpt
   ```
2. **完整性校验**：上传后用**大小 + MD5 双校验**确认与本地一致（本地 `policy_best.ckpt` 与服务器 `policy_last.ckpt` 的 MD5 必须相同）；
3. **上传失败自动补传（watcher）**：独立后台进程定期扫描"本地有检查点但服务器缺失"的任务，自动带重试补传，上传成功后同步更新演示页与结果清单——防止单次失败导致检查点遗漏。

## 4. 检查点验证（防止"假成功"）

**经验**：
1. 训练日志应输出**验证集 loss + 最优 epoch**，并保存 `policy_best.ckpt`（验证 loss 最优）而非盲目用末轮；
2. 部署前在服务器环境（torch 版本可能与本机不同）加载检查点做一次**前向推理**，确认 state_dict 兼容；
3. 用 `policy_best.ckpt` 作为部署文件（复制为 `policy_last.ckpt`），保证线上是最优模型。

## 5. 任务调度的幂等与自愈

**经验**：
1. 训练驱动以**服务器上的检查点是否存在**为幂等判据（`server_ckpt_ok`）：已上传的任务重启后自动跳过；
2. 并行数据转换会写共享 `TASK_CONFIGS.json`，采用"训练前自愈补齐 + 独立配置锁"避免竞态丢条目；
3. 训练失败保留数据便于排查，不静默丢弃。

---

**小结**：大规模训练+部署的可靠性 = 数据生命周期管理 + 连接频率控制 + 断点续传 + 完整性校验 + 幂等自愈。这些经验让 12 任务训练在共享、受限环境下稳定跑通，并保障线上检查点的质量。
